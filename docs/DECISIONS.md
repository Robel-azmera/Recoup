# Decisions

These are choices made where the spec (`SOLUTION_DESIGN.md`) was ambiguous or had to give way to the brief. Each one is the simplest option that keeps the demo working end to end.

| # | Decision | Why |
|---|---|---|
| D1 | **The backend is Python 3.12 + FastAPI**, not the Node/Fastify the spec lists. | The build brief overrides the spec's stack table. Everything else in the spec is unchanged: workflows, data model, agent design and policy gate. |
| D2 | **Pydantic models are the only schema source.** TS types are generated from FastAPI's OpenAPI (`pnpm gen:types` → `packages/shared/src/api.d.ts`). All models in `app.models.SCHEMA_MODELS` are injected into the OpenAPI components, even if no route references them yet. | One contract for the API, Firestore docs and LLM structured output, with no drift. |
| D3 | **Money is stored as integer minor units plus an ISO currency code**, as Stripe does it. Formatting happens only in the UI with `Intl.NumberFormat`. | Avoids float rounding in reconciliation. |
| D4 | **Storage sits behind a `Store` protocol.** `FirestoreStore` (firebase-admin, blocking calls in `run_in_threadpool`) runs in dev and prod. `MemoryStore` runs tests. `Store.create` is atomic and returns `False` if the doc exists. That one primitive dedupes webhooks (`webhook_events/{event.id}`) and makes jobs idempotent. | Tests need no emulator, and dedupe stays correct under concurrent deliveries. |
| D5 | **firebase-admin initialises lazily.** With `FIRESTORE_EMULATOR_HOST` set it uses anonymous credentials. | Importing the app (tests, OpenAPI dump) never needs Google credentials. |
| D6 | **Every external integration has a mock.** Real Stripe, Gemini, Telegram, Calendar and Resend are used only when their keys are set. `/healthz` and the Overview screen show `live` or `mock` for each one. | Every phase can be demoed before credentials arrive. |
| D7 | **The dev runner is a honcho `Procfile`** started through `scripts/dev.sh` / `scripts/dev.ps1` (or `pnpm dev`). The wrapper sets `PYTHONUTF8=1`, because honcho crashes on Vite's Unicode output under the Windows cp1252 console. | `make` isn't available on Windows; the brief allows honcho. |
| D8 | **The emulator uses project id `demo-recoup`** and keeps no state between runs. `scripts/seed.py` rebuilds everything. | `demo-*` ids stop the emulator from touching real GCP. Re-seeding is quicker than managing exports. |
| D9 | **Only text evidence fields are drafted**, in `StripeEvidence`. File fields (`customer_communication`, `shipping_documentation`, …) need uploaded file ids, so customer messages are quoted in `uncategorized_text` with their source ids. | Keeps submission a single API call. File upload can be added later. |
| D10 | **Grounding is checked per sentence.** `EvidenceDraft.sentences[]` holds `{id, field, text, source_ids}`. `citations` (sentence id → source ids) and `unsupported_sentence_ids` are computed fields, and the policy gate blocks submit while any sentence is unsupported. | Rule 3 of the brief, enforced by a deterministic check rather than by the model. |
| D11 | **Recoup's `DisputeStatus` (workflow state) is kept apart from Stripe's raw `stripe_status`.** | The UI and the policy state machine need states Stripe doesn't have, such as `drafting` and `awaiting_approval`. |
| D12 | **Datetimes are stored as ISO-8601 UTC strings** (`to_doc` = `model_dump(mode="json")`), and `utcnow()` truncates to whole seconds. | The same representation works in Firestore, the in-memory store and the generated TS types (`string`). ISO UTC strings sort correctly, so range queries and `order_by` work. |
| D13 | **Demo auth.** `POST /auth/login` with the admin password returns an HMAC bearer token for the API plus a **Firebase custom token** with `{admin: true}`. Firestore rules allow reads only to `admin` tokens, and only on the live-feed collections (`audit_log`, `disputes`, `recon_*`, `proposed_actions`, `fraud_warnings`). All writes go through the API. The feed falls back to polling `GET /audit` if Firebase sign-in fails. | The live listeners the brief asks for, without public read access to dispute data. Verified against the emulator: admin 200; anonymous, non-admin and `orders` all 403. |
| D14 | **Reconciliation runs on planted ledger data.** Test-mode payouts can't be steered into anomalies, so `seed_data.py` writes 28 historical orders with synthetic charges, five payouts and balance txns containing six planted anomalies (`PLANTED`). The 12 recent orders are charged through Stripe, real or mock, so they produce real dispute and early-fraud-warning events. Recent charges are too new to be due in a payout, so the two sets never double count. | The recon demo is deterministic and every exception type is testable, while W1 and W2 still use real Stripe objects. |
| D15 | **Stripe test PaymentMethods**, from docs.stripe.com/testing: `pm_card_createDispute` (fraudulent), `pm_card_createDisputeProductNotReceived`, `pm_card_createDisputeInquiry` and `pm_card_createIssuerFraudRecord` (early fraud warning). Outcomes are forced in test mode with `winning_evidence` / `losing_evidence` in `uncategorized_text`. | The documented way to get real disputes in test mode. |
| D16 | **The mock Stripe keeps Stripe-shaped dicts in the store** (`_mock_stripe_*`), so the seed script and the API share state. It emits events through the same `EventProcessor`, including dedupe, that real webhooks use. It spreads mock `due_by` over 2–11 days so the deadline list and sweep have variety. | Mock and real follow one code path, so a demo on mocks shows real behaviour. |
| D17 | **Webhook failure handling.** The dedupe record is created atomically before processing. If a handler raises, the record is marked `failed` and the API returns 500 so Stripe retries. A retry of a `failed` event is reprocessed, never deduped. | Exactly-once effects without losing events to transient errors. |
| D18 | **The agent loop has two parts.** (1) A tool-calling loop capped at **8 tool calls in total**, counted across turns; calls past the budget, unknown tools and invalid arguments go back to the model as errors. (2) One structured call with `DisputeAnalysis` as the Gemini response schema, validated by Pydantic, with one retry that feeds the validation error back. | Gemini 2.5 can't combine function calling with a JSON response schema in one request. |
| D19 | **The checklist and a baseline score are deterministic.** Each playbook item names an evaluator, so the checklist is computed from tool records. The baseline is weighted evidence coverage, capped at 45 when required evidence is missing. Gemini writes the rationale and its own score, but the score is **clamped to the baseline ±20**. | The checklist never depends on the LLM, and scores stay explainable and stable between runs. |
| D20 | **Grounding is more than citation presence.** A sentence is unsupported if it cites no known record, or if any checkable fact in it is missing from the records it cites: amounts, dates, ids or tracking numbers, emails, URLs, quoted text. Factual Stripe fields (tracking, addresses, IP, policies) are copied from records by code (`author: system`), never written by the LLM. | Catches invented details even when a citation is present. |
| D21 | **Analyst edits:** original sentences found verbatim in the edited text keep their citations, and any new text becomes `author: user`. The analyst attests to it, so it doesn't need a citation. Every edit re-proposes the submit action, which gives it a new hash, supersedes the old action and invalidates old approval tokens. | Rule 3 targets LLM output; requiring citations on a human's own words would block legitimate edits. |
| D22 | **ProposedAction ids derive from the payload hash** (`act_<sha256[:20]>`), so identical proposals are idempotent. Approval tokens are an HMAC over (user, action id, hash, expiry), lasting 30 minutes. Approval re-runs every rule against fresh state, then takes an `action_locks/{id}` create-lock, so concurrent approvals (UI + Telegram) execute exactly once. The Stripe idempotency key is `recoup-<action id>`. | Approval binds to exactly what the human saw, and money moves at most once. |
| D23 | **Test-mode outcome forcing:** `settings.demo.force_test_outcome` (default `won`) goes into the *approved payload*. The executor appends `winning_evidence` to `uncategorized_text` only when `livemode` is false. Still to check with a real key: whether Stripe needs the field to *equal* the magic value or only to *contain* it. If it needs equality, switch the executor to replace mode. | The demo shows real close/won webhooks; the forcing is visible and hashed, not hidden. |
| D24 | **LLM fallback:** if Gemini fails after retries, the agent builds a deterministic draft from the same tool records (`model: deterministic-fallback`) and audits `agent.llm_fallback`. Without a key, `MockLLM` runs the same loop (real tool calls, real audit steps). | The demo never stalls on free-tier quotas, and the fallback still passes grounding. |
| D25 | **Draft cache key:** `sha256(prompt version, model, instruction, fingerprint of dispute + order + messages + charge + policies)`. A regenerate with nothing changed costs no Gemini calls. | Rule 6 (cache drafts) and free-tier discipline. |
| D26 | **Output schemas mark defaulted fields as required** (`json_schema_serialization_defaults_required`), so generated TS types match what the API actually returns (`checklist: ChecklistItem[]`, not `ChecklistItem[] \| undefined`). | No non-null assertions scattered through the UI; the generated types stay honest. |
| D27 | **Firestore is the change signal, the API is the data source.** The web app listens to `disputes`, `proposed_actions` and `recon_*`. When a snapshot changes, it invalidates the matching TanStack queries and refetches from the API. Without the Firebase sign-in, queries poll every 5s, and the workspace polls every 1.5s while the agent drafts. | One data shape (the API's), live updates without duplicating read logic in the browser. |
| D28 | **The mock charge is backdated to the order's time; the mock dispute and its `due_by` are relative to "now".** Real Stripe always stamps charges "now", so in live test mode the timeline shows the payment at seed time. | A coherent timeline in the mock demo, with deadlines always in the future. |
| D29 | **Bulk accept** (Disputes list) is limited to disputes the agent recommends accepting. Each one still goes through propose, approval token, gate and execute; there's no bulk bypass. | The spec's "bulk-accept low-value losses" without weakening the gate. |
| D30 | **Reconciliation thresholds** (`ReconConfig`): a charge must appear in a payout within **7 days** (new Stripe accounts settle on a 7-day schedule). The fee is checked against 2.9% + 30¢ with a tolerance of max(25¢, 20%). A payout is delayed when it is still pending or in transit **24h** past its arrival date, or has failed. A duplicate is the same customer email or card and the same amount within **30 minutes**, where exactly one of the two charges has no order. Payout totals are also checked against the sum of their transactions' net (reported as `amount_mismatch` on the payout). | Conservative defaults that catch every planted anomaly with no false positives on the seeded data (asserted in `test_recon_engine.py`). |
| D31 | **Exception lifecycle.** Ids are `rx_<sha256(type + sorted refs)>`, so re-runs update rather than duplicate. Analyst decisions (resolved, snoozed, expected) persist across runs. An expired snooze reopens. An open exception that is no longer detected is auto-resolved (`resolved_by: system`), and reopens if it comes back. Triage actions change only Recoup's own records, so they are audited but not gated. | Jobs can be re-run safely (rule 2), and the analyst's work is never lost. |
| D32 | **Recon explanations:** one batched Gemini call per run, for new exceptions only, and cached on the exception. Each explanation and suggested action must pass the same fact-containment check as rebuttals (amounts, ids and dates must be in the exception's facts); otherwise a per-type template is used (`explained_by: template`). | Free-tier friendly, and an explanation never invents numbers. |
